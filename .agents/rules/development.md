# 开发流程

## 开始前

1. MUST 先阅读根目录 `AGENTS.md` 列出的工作流，再开展开发。
2. MUST 检查仓库路径、当前分支、工作树列表、暂存区和未跟踪文件，保护用户已有修改；不得通过 reset、强制切换或清理让工作区“看起来干净”。
3. 多步骤任务先说明目标、范围与验证方式。不明确的需求先向用户提问，不擅自补全产品决策。

## main 与工作树

- `main` 是受保护的主分支。首个内容提交按用户明确授权直接初始化 `main`；该例外仅限此次初始化，之后所有修改 MUST 从开发分支通过 PR 合并到 `main`，不得直接提交或推送到 `main`，不得绕过保护。
- 开始新需求前 MUST 获取远端最新状态，确认本地 `main` 的暂存区、已跟踪文件与未跟踪文件均干净，且本地 `main` 与 `origin/main` 提交一致。可用 `git fetch origin`、`git status --short` 和提交比较确认；仅在可以快进时同步主分支。有分叉或用户改动时停止相关操作并向用户说明，不自动重置或暂存用户工作。
- MUST 从同步后的 `main` 创建新的开发分支和 Git 工作树，在该工作树开发，不在主分支工作目录开发。首次推送尚未发生、`origin/main` 尚不存在时，应先完成获授权的初始化发布，再启动后续需求。
- 分支名推荐 `<user>/<feature-name>`。`user` MUST 先向当前用户确认，不从其他开发者或历史会话的约定推断。同一会话中已确认的前缀可继续使用；个人前缀不写入通用规则。
- `feature-name` 按主要需求命名，使用简洁的 kebab-case，例如 `<user>/archive-import`、`<user>/fix-answer-feedback`。本地工作树建议放在仓库同级的独立目录中，不混入项目源码或公开产物。

## 开发、验证与交付

1. 保持需求范围集中，不附带修改题目、答案、视觉或交互。迁移时保留既有页面行为与正式域名，需调整时按用户要求处理。
2. 进行与改动相称的本地验证。页面变更检查桌面、窄屏、资源请求、键盘操作和关键交互；纯文档修改检查内容、链接与 diff。不为工作流初始化引入前端依赖。
3. 不提交工作日志、会话记录、验证过程或交接日志。需要跨会话保留的临时记录可放在已忽略的 `.agents/local/` 下；正式规则维护在工作流文档中，交付说明与必要验证结论写入 PR。
4. 按 `git.md` 拆分并提交变更；确认当前工作树干净，再推送开发分支并提出 PR。若发现需求外改动，先报告并处理归属，不擅自提交或删除。
5. PR 以 `main` 为目标，等待审阅及所需检查；不得将用户要求提出 PR 理解为自动批准合并。合并和工作树清理按用户授权处理。
6. 完成时明确说明本地修改、提交、推送、PR、合并和部署分别完成到哪一步。未经实际发布和线上验证，不称为“已上线”。

## 仓库保护

上述保护是开发约定。GitHub 上的分支保护或 Ruleset 需要单独配置；文档和本地 Git 不会自动启用远端保护。未启用时仍 MUST 遵守 PR 流程，不借此直接修改 `main`。
