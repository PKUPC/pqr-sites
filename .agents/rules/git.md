# Git 提交与 PR 规范

## Semantic 提交

提交信息 MUST 使用以下结构：

```text
<type>(<scope>): <summary>
```

`scope` 可省略；`type` 和可选的 `scope` 使用小写，摘要简洁、准确，可使用中文。常用类型：

| type     | 用途                 |
| -------- | -------------------- |
| feat     | 新功能               |
| fix      | 问题修复             |
| docs     | 文档与工作流约定     |
| refactor | 不改变外部行为的重构 |
| style    | 格式调整，不改变行为 |
| test     | 测试变更             |
| build    | 构建与依赖配置       |
| ci       | 持续集成配置         |
| chore    | 其他维护工作         |
| revert   | 撤销既有提交         |

例如：`docs: 初始化 PQR 项目介绍与协作约定`、`fix(unicode-plus-one): 修复答案反馈`。破坏性变更使用 `!`，并在正文说明 `BREAKING CHANGE:`、影响与迁移方式。

## 一个提交只做一件事

- 每个提交 MUST 只处理一个需求或问题；同一需求必要的实现、验证和说明可以放在一起。
- 如果待提交区域包含多个不同需求或修改，MUST 尝试拆分成多个提交，可按文件或差异块暂存。确实无法合理拆分时，先向用户说明耦合原因，再确定提交范围。
- 提交前 MUST 审阅暂存 diff，检查无意修改、敏感信息及验证结果；不得直接把整个工作区中不明归属的修改加入提交。
- 不绕过提交检查，不擅自改写已共享历史或强制推送。

## PR 交付

- 按 `development.md` 完成开发与验证，MUST 在当前工作树干净的情况下提出 PR，目标为 `main`。
- 标题概述该分支的主要变更；正文说明开发了什么、修复了什么、验证了什么，以及实际存在的限制。
- 每项修改 MUST 提供方便审阅的入口文件链接，必要时注明关键符号或位置。说明应面向未读过聊天记录的审阅者，不复制过程流水账。
- 新页面等涉及较大 UI 变动的需求，MUST 在 PR 中添加可直接查看的实际页面截图，标明对应页面与视口；按改动范围展示桌面和窄屏效果，截图不包含敏感信息。
- PR 内容应与最终实现一致；需求范围变化后同步更新标题与正文。纯文档变更不要求页面截图。
